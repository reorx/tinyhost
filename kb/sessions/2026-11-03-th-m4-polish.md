## 实现说明

### 问题 1：`-h` 不列 flag

- 新增 `cmd/tinyhost-server/flags.go`：`parseFlags` 先把每个 flag 对应的 `TINYHOST_*` 变量用 `FlagSet.Set` 套上，再解析命令行（命令行优先，变量格式错误和 flag 格式错误一样报错）；遇到 `-h` / `--help` 把用法写到 stdout 并返回 `flag.ErrHelp`，`run` 把它当成功（退出 0）。用法里每个 flag 一段：`--name 类型`、中文说明（带编译时默认值，不是环境变量的值）、`环境变量 TINYHOST_X`。
- 所有子命令都走它：`serve`、`gc`、`healthcheck` 共用同一组 flag（`gc`、`healthcheck` 的说明写明只用到哪几个）；`passwd` 和 `token create` 的 `--data-dir` 也改成统一机制（原来是单独的 `env()` 函数，已删）；`token create` 的 `--name`、`--ttl` 不读环境变量，帮助里也不写。`version -h`、`token -h`、`help serve`（等于 `serve -h`）、顶层 `-h` 都能用。顶层帮助按名字列出命令和一句说明。
- 行为差异：`token create`、`passwd` 多出的位置参数现在报 `unexpected arguments`，原来是各自的提示语；退出码都是 1。

### 问题 2：未设密码时静态资源被拦

- `adminMiddleware`：没设密码时，`GET`/`HEAD` 且路径以 `/static/` 开头、并且是规范路径（`path.Clean(p) == p`）的请求交给 mux，其余照旧返回初始化页。规范路径的要求挡住了 `/static/../agents` 这类路径（否则 mux 会 301 到 `/agents`，虽然也拿不到页面），`/static/` 目录列表也不放行。
- 测试从初始化页里抽出所有 `/static/` 资源逐个请求，内容要和 embed 的文件一致且不是 HTML；`/login`、`/agents`、`/apps/demo`、`/events`、`/staticx`、`/static/`、`/static/../agents`、`POST /login`、`POST /apps`、`POST /static/admin.css` 都必须是初始化页，且没有创建 App。

### 问题 3：探活

- 服务端：`GET|HEAD /_/health` 在 Host 分流之前处理，所以 apps、admin 和任何 Host（包括 `127.0.0.1:3471`）都能访问。它跑一次 `PRAGMA user_version`（新增 `Store.Ping`，2 秒超时），成功返回 200 `ok\n`，失败返回 503 `unavailable\n` 并记错误日志；带 `X-Tinyhost-Version`、`Cache-Control: no-store`、`nosniff`，不设 cookie，其他方法 405。探活请求不进请求日志，避免每 30 秒一行。
- `tinyhost-server healthcheck`：用和 `serve` 相同的 flag 和环境变量，只取 `--listen`；监听地址是空主机或 `0.0.0.0` 时连 `127.0.0.1`，`[::]` 时连 `[::1]`。HTTP 客户端 5 秒超时、不走代理；200 才算健康，打印 `ok` 退出 0，否则错误日志写 stderr、退出 1。不打开数据库、不建目录、不需要凭证。
- 为什么不看 Host：恢复演练脚本那种 `command: [serve, --apps-url ...]` 的用法里，apps-url 只在 CMD 参数里，HEALTHCHECK 看不到；不依赖 Host 就不受影响。

### 问题 4：重试

- `skill/install.sh`：整个脚本的动作放进 `main`，最后一行 `main` 才执行。这样 `curl | sh` 收到截断的脚本时什么都不跑（测试逐行截断，每个前缀都不调用任何外部命令）；curl 的 `--retry-all-errors` 在输出到管道时，失败重试会把已经输出的部分再输出一次，此时 sh 读到的是「前半段 + 完整脚本」：前半段停在函数体中间时会把后面的内容吞进函数体并以语法错误结束，停在函数定义之后时只是重复定义一次，两种情况都不会执行半截动作。
- install.sh 的两次下载（checksums 和 CLI 包）用 shell 循环重试 3 次，间隔 1、2、4 秒，curl 和 wget（含 busybox wget）都一样；每次失败在 stderr 提示「下载失败，N 秒后重试」。没有 curl 也没有 wget 时立即退出，不重试。
- SKILL.md 和 apps 根路径说明页：`curl -fsSL --retry 3 --retry-all-errors <server>/install.sh | sh`。命令由 `skill.InstallCommand` 生成，根路径页直接用它，SKILL.md 里是同样的字面量，测试保证两处一致。curl 自带的 `--retry` 只把 408/429/500/502/503/504 和超时当作临时错误（本机 curl 8.7.1 的 man 页确认，不含 Cloudflare 的 522），所以必须加 `--retry-all-errors` 才能重试 52x 和连接重置。
  - curl 版本：`--retry-all-errors` 是 7.71.0（2020-06）加的。macOS 12 起自带的 curl 都更新（本机 8.7.1）；Debian 11（7.74）、Ubuntu 22.04（7.81）、24.04（8.5）、Alpine 当前版本、GitHub runner 都支持；Ubuntu 20.04（7.68）、RHEL/Rocky 8（7.61）、CentOS 7（7.29）不支持，会报 `option --retry-all-errors: is unknown`。SKILL 里写了「curl 报这个选项未知就去掉它再跑一次」。没有改成「先下载到文件再执行」，因为那样 README、根路径页和所有已有说明的一行安装方式都要变。
  - SKILL 里直接用 curl 上传的示例不加重试，并补了一句：上传不要加重试选项，遇到 52x 先查版本再决定是否重传；CLI 只重试只读请求。
- `scripts/accept-install.sh` 用和 SKILL 相同的安装命令，取 `/skill.md` 的 curl 也加了重试；新增测试：install.sh 第一次 522 时验收仍然通过。原来「install.sh 一直下载失败时报安装失败」的测试保留，现在多等约 7 秒重试。
- **CLI 的结论：改了，只对 GET。** `whoami`、`apps`、`info`、`versions`、`previews` 和 login 里检查已有凭证的 whoami 是只读的，遇到连接失败（不含客户端超时）或 502/503/504/520–524 时最多再试 2 次，间隔 1、2 秒。理由：Agent 在云端遇到偶发 52x 的概率和安装时一样，GET 重放没有副作用，代价只是持续故障时多等 3 秒。上传（deploy、data push、preview）、promote、DELETE、logout、设备授权的 POST 一律只发一次：522 时请求没到源站可以重放，但 524 时源站可能已经处理，CLI 分不清。测试用一个模拟 CDN 的代理确认 GET 各发 2 次、写请求各发 1 次、持续 522 时一共 3 次。

### 问题 5：镜像以 nonroot 运行

- Dockerfile：unpack 阶段建 `/tmp/data`（0700，属主 65532:65532），最终镜像 `COPY --from=unpack --chown=65532:65532 /tmp/data /data`，放在 `VOLUME /data` 之前（VOLUME 之后对该路径的改动会被丢弃）；`USER 65532:65532`；`HEALTHCHECK --interval=30s --timeout=10s --start-period=30s --retries=3 CMD ["/tinyhost-server", "healthcheck", "--listen", ":3471"]`。ENTRYPOINT、CMD、EXPOSE 不变，基础镜像仍是 `distroless/static:latest`。
- 静态测试 `scripts/dockerfile_test.go` 检查以上几行和顺序，并且 CMD 保持部署依赖的形式。真实行为在 release 流水线里验证：新增一步检查镜像 config 的 `User` 是 `65532:65532`、Healthcheck 调用 `healthcheck`，然后在 amd64、arm64 上各用一个全新命名卷 `docker run -d -v NAME:/data`，等 Docker 报 healthy，再 `docker exec ... token create` 证明 65532 能写这个卷。
- 兼容：线上 compose 本来就 `user: 65532:65532`，数据目录属主是 65532，不受影响；升级后 compose 会自动用镜像的 HEALTHCHECK（`.env` 里 `TINYHOST_LISTEN=:3471`，和写死的 `--listen :3471` 一致；只读根、`cap_drop: ALL` 下 healthcheck 不写任何文件）。
- 命名卷：Docker 第一次把空的命名卷挂到 `/data` 时，会把镜像里 `/data` 的属主和权限复制过去，所以 README 的 `docker volume create` + `docker run -v tinyhost-data:/data` 不用改也能写入。已经被 rc.1（root）初始化过的卷，属主是 root，换新镜像后 65532 写不进去，需要一次 `chown`（见 README 一节）。
- bind mount：宿主目录原样挂进去，Docker 不改属主。要求：宿主目录属主 65532:65532（或对 65532 可写），建议权限 0700，例如 `sudo install -d -o 65532 -g 65532 -m 700 /srv/tinyhost/data`。也可以用 `--user` 换成宿主上已有的 UID，但运维命令（`docker exec ... passwd|token|gc`）会继承同一个用户。
