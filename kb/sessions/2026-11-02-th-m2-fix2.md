# 修复私有 App 首次登录的 CSP 回跳阻断

## 概要与实现说明

Chrome 将登录表单 POST 后的整个 302 链作为表单导航处理。登录页面原先的 `form-action 'self'` 会阻止 `/view-auth` 跳转到 apps 的 `/_/auth`，即使后台会话已成功建立，浏览器也无法自动回原页面。

选择任务建议的第一种修法：在 `adminMiddleware` 中仅对精确路径 `/login` 的响应，把经过 Config.Validate 校验的 apps 源追加到 `form-action`。移除配置允许的尾部 `/`，保留 scheme、host、端口，避免把源变成路径限制。GET 登录页、密码错误后的登录页和登录成功的 302 响应均保持同一策略。

这样保留了已有票据交换、302 跳转和无 JavaScript 登录流程，不需要增加中间页、meta refresh 或外部导航脚本。除了登录流程的这一个明确源之外，不增加其他表单目的地；`default-src 'self'`、`frame-ancestors 'none'`、后台 POST 来源检查、查看票据和 `safeNext` 均保持原逻辑。已登录用户访问 `/view-auth` 仍直接返回 302。

## 修改的文件

- `internal/server/admin.go`：为登录响应增加精确的 apps 源 CSP 例外，注释说明 Chromium 重定向链兼容原因。
- `internal/server/login_csp_test.go`：行为测试覆盖 HTTP 默认源、HTTPS 非默认端口和尾斜杠；断言登录三类响应与其他后台响应的完整 CSP、原 next 和 ticket 兑换地址。
- 本总结：修复理由、TDD 证据、真实浏览器结果和交接建议，与代码一起提交。

5. 浏览器 B 保有后台/查看状态时，打开真实 deploy 的公开 malicious-app。脚本发送批准、删除、改可见性及六类 Agent API 请求，包含 fetch 和自动 POST 表单共 18 次；CDP 记录在 `security-network.json`，归并结果在 `security-requests.json`。
6. 六次后台请求全部 403；其余 11 次 API 请求 401，一个不支持的方法 405。同源 API 请求实际携带 th_view。数据库前后 2 Apps、1 待批准申请、5 审计、2 版本、1 Agent，全部所选字段一致；目标仍私有、未删除，授权申请仍 pending。见 security-before.json / security-after.json 与 evidence-report.log。
7. 浏览器 A 已有 admin 会话、尚无 viewer，直接访问私有子路径 `?proof=existing-admin`；四次全为 GET，自动回原路径并返回 200，没有登录页。见 existing-admin-network.json。

本机 Chrome 将 localhost 与 admin.localhost 视为 cross-site，后台跨域 fetch 的 admin cookie 被 SameSite=Lax 阻止；请求仍以恶意 Origin 获得 403。生产同站携带 admin/viewer cookie 的分支由未改动且本次通过的 `TestAppPageCannotPerformControlledActions` 覆盖，不将本地截图称为生产 same-site 手验。`TestViewAuthRejectsOffsiteNext` 和 `TestAdminPostWithoutOriginRejected` 本次也通过。
