## 恶意脚本测试及前后对比

恶意 App 的源码在工作目录 `malicious/`，生成器为 `build_attack.py`。使用平台真实 deploy 上传，不由浏览器注入替代页面脚本。页面将每个请求的结果写进表格；同源 API 响应可读，跨域后台响应因 CORS 和 frame-ancestors 不能读，因此以独立 CDP 网络、服务端状态和数据快照共同判定，未把 TypeError 单独当成鉴权通过证据。

初轮在改名之前执行 20 次请求，额外探测了不存在的 POST 创建接口；有 3 次 405，其中 2 次来自不存在接口，另一次为表单无法使用 DELETE。此轮前后快照为 `security-before.json` / `security-after.json`：2 Apps、5 申请、13 审计、4 版本、3 Agents，全部字段一致。原始 HAR 已解析为脱敏 `security-network.json` 并删除，CORS fetch 在 HAR 中的 status=0 由服务端日志的 403 补证。

最终轮在 App 改名、恢复之后重新生成目标，去掉不存在的创建接口，以有效待批准申请和现有私有 App 为目标。9 个目标分别执行 fetch（`credentials: 'include'`）与自动 `<form method="post">`，共 18 次：

| 目标 | fetch | 自动 POST 表单 |
|---|---|---|
| 后台批准待批准申请 | 403（页面因 CORS 显示 TypeError） | 403（响应不能嵌入） |
| 后台删除现有 App | 403 | 403 |
| 后台把私有改为公开 | 403 | 403 |
| Agent API 发布包、推数据、切主入口、logout | 各 401 | 各 401 |
| Agent API 撤覆盖目录 | DELETE 401 | POST 同一路径仍 401 |
| Agent API 删除 App | DELETE 401 | POST 为不支持的方法，405 |

`security-observed-before.json` / `security-observed-after.json`：2 Apps、5 申请、19 审计、4 版本、3 Agents，全部快照字段完全相同。待批准申请仍 pending；目标 App 仍私有、未删除、主入口仍 v3。`evidence_report.py` 对这些断言、请求数量及状态作了核对，输出在 `evidence-report.log`。`security-observed-network.json` 保留 98 条脱敏 CDP 事件，`security-observed-requests.json` 整理为 18 个请求，统计为 **6×403、11×401、1×405**。

取证限制：Chrome 将 `http://localhost` 与 `http://admin.localhost` 判为 `cross-site`。后台 fetch 虽设 credentials=include，其 `th_admin` 被 `SchemefulSameSiteLax` 阻止；三次 fetch 的 Origin 明确为 apps 源，仍得到 **403 而非缺会话的 401**，证明走了 Origin 拒绝路径。所有同源 API fetch/表单实际带 `th_view`（已由 ExtraInfo 记录验证），仍无法写入。此处不声称手验了生产两个 reorx.com 子域的 same-site cookie 发送行为；该分支由既有 `TestAppPageCannotPerformControlledActions` 使用恶意 Origin、same-site 和 admin/viewer cookie 覆盖，本任务未重跑全仓测试。

## 交给协调者

### 阻塞签收：首次私有登录被 CSP 阻断（验收 7）

复现步骤：

1. 发布 App，再在后台设为私有。
2. 新浏览器无 admin/viewer cookie，访问 `http://localhost:3471/accept-renamed/nested.html?proof=return`。
3. 浏览器跳转 `admin.localhost` 的登录页；输入正确密码并点击登录。
4. 密码 POST `/login` 返回 302，随后 GET `/view-auth?...` 携带有效 `th_admin`，也返回 302。
5. 期待继续 GET apps 的 `/_/auth` 换 viewer cookie，最后显示原子页面、保留 query；实际这一步没有发出，浏览器停在登录页。

`private-login-csp.json` 同时记录服务端成功响应、admin cookie 确实发送、`Network.loadingFailed: net::ERR_ABORTED`，以及 Chrome 错误：`Sending form data ... violates ... "form-action 'self'"`。初次失败、重复点击、延时原生 `requestSubmit()` 都能复现，已排除仅凭 agent-browser 返回过早误判。手动重新打开原 App 链接可走 GET 导航完成兑换，但这不满足自动返回要求。

原因：`internal/server/admin.go` 为所有 admin 页设置 `form-action 'self'`；从登录表单开始的 302 链最终跳到另一个 apps 源，Chromium 会将它算作表单导航并受该 CSP 限制。这是 spec 同时要求严格表单源与跨域登录自动返回产生的实际兼容问题。

建议修复时保留 Origin 校验和 CSP；可考虑仅对登录流程允许配置中的 apps 源，或者在 admin 源结束表单重定向链，再用独立页面导航跳 apps。不要直接移除 form-action 或改为通配符。修复后应复跑「全新浏览器 → 私有子路径+query → 登录 → 自动返回」，并重新核对恶意后台 POST 仍然 403。

按 brief 的共享文件归属，本任务未修改 `kb/known-issues.md`、AGENTS.md、next-up 或 plan/spec 勾选框。请协调者把此问题登记到 known-issues；第 7 条修复复验前保留 M2 未签收状态。fix1 的标题保留在实际二次 deploy、推数据、改名和恢复之后仍正常，未发现标题回退。
