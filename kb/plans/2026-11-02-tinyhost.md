# tinyhost：给 Agent 用的自托管静态网站发布服务

## PRD

### 背景

我会让各种云端 Agent（ChatGPT Agent、Grok、Codex cloud 等）帮我干活。很多结果需要"看"：数据可视化、内容预览、让 Agent 设计的小网站。这些产物现在留在 Agent 的沙箱里，我看不到，也没法分享。

我需要一个自部署的地方：Agent 一条命令把一个目录发布成网页，把链接告诉我，我点开就能看。Agent 要能自己接入这个服务，我只点一下批准，而不是手动给每个 Agent 开账号。

同类项目（here.now、plannotator/artifact-server、open-artifacts 等）要么是托管服务，要么面向团队、依赖 Node 和多个注册域名，部署偏重。tinyhost 的定位是个人使用、可开源、一个 Go 二进制加一条反代配置就能跑起来。

### 目标

- Agent 在任何能联网的沙箱里，读一份说明就能完成：安装 CLI → 申请授权 → 预览 → 发布，然后把链接交给我。
- 我只做两件事：在手机或电脑上批准 Agent 的授权申请；打开链接看结果。
- 写 App 的 Agent 和整理数据的 Agent 可以分开发布，互不覆盖。
- 每次发布都留下不可变的版本，误操作可以一键回滚。

### 核心概念

| 概念 | 说明 |
|---|---|
| App | 一个发布单元，有一个全局唯一、固定的路径名（slug），例如 `q3-report` |
| App 包 | `tinyhost deploy` 上传的整个目录：HTML、JS、CSS、图片，也可以带示例数据 |
| 覆盖目录 | `tinyhost data push` 上传到 App 下某个目录（如 `data/`）的内容。访问这个目录时只看覆盖内容，App 包里的同名目录被整体盖住 |
| 版本 | 每次发布（App 包或数据）生成一个新版本 vN，是那一刻 App 包和所有覆盖目录合起来的快照，内容永不改变 |
| 主入口 | App 当前指向的版本。发布默认让主入口指向新版本，也可以切回任意旧版本（回滚） |
| 预览 | 临时发布，不属于任何 App，用一个带随机串的私密链接访问，到期自动失效 |
| Agent | 经我批准、拿到 token 的一个客户端（一台云电脑、一个 Agent 环境） |
| Owner | 我，唯一的人类用户，用密码登录后台 |
| 可见性 | App 是公开（任何人可看）或私有（我登录后才能看）。新建 App 默认私有 |

### 域名与 URL

两个域名，最小部署时都指向同一个服务：

- **`th.reorx.com`**：App 内容、预览、Agent 用的接口、安装脚本和 skill。
- **`th-admin.reorx.com`**：管理后台、授权批准页、我的登录。我的密码只在这个域名下输入。

| 用途 | 地址 |
|---|---|
| App 主入口 | `https://th.reorx.com/q3-report/` |
| 某个版本 | `https://th.reorx.com/q3-report@v3/` |
| 预览 | `https://th.reorx.com/_p/<随机串>/` |
| 安装脚本 / skill | `https://th.reorx.com/install.sh`、`https://th.reorx.com/skill.md` |
| 管理后台 | `https://th-admin.reorx.com/` |

- slug 规则：小写字母、数字、连字符，以字母或数字开头和结尾，长度 3–40，不能有连续两个连字符。`_` 开头的路径留给系统。
- `/q3-report` 自动跳转到 `/q3-report/`。
- App 改名后，旧路径永久跳转到新路径，已经发出去的链接不会失效。
- **App 只能用相对路径**（`./app.js`、`data/sales.json`），因为同一份内容会同时挂在主入口、版本、预览三种前缀下。单页应用用 hash 路由。CLI 上传前会检查以 `/` 开头的引用并给出提示。

### 权限

| 操作 | Agent | Owner（后台） |
|---|---|---|
| 查看所有 App 的列表和信息 | ✓ | ✓ |
| 创建 App（创建时可指定公开或私有） | ✓ | ✓（也可以先建一个空 App、定好路径） |
| 给任意 App 发布新版本、推数据、撤掉覆盖目录 | ✓（包括别人创建的） | ✓ |
| 把主入口切到任意版本（回滚） | ✓ | ✓ |
| 删除 App | 只能删自己创建的；进回收站，7 天后清理 | 任意 App；可恢复，也可立即清理 |
| 改可见性、改 slug、删除某个版本 | ✗ | ✓ |
| 创建、查看、删除预览 | 只限自己的 | 全部 |
| 批准授权、手动签发 token、撤销 Agent | ✗ | ✓ |

App 页面里的脚本做不了任何受控操作：受控操作只认 Agent 的 token 或后台会话，App 页面两样都拿不到。私有 App 的登录只授予"查看"。

### 不做的事（v1）

- 后端运行时（Node / Python 进程）。数据模型为它留了口子，但 v1 只托管静态文件。
- 自定义域名、每个 App 独立子域名。
- MCP 接入（让没有终端的对话式 Agent 直接发布）。
- 评论、访问统计、搜索引擎收录。
- 文件变化后自动重新预览（watch）、热更新。
- 多个人类用户、团队、细粒度权限。
- Windows 的一行安装脚本（Windows 上手动下载二进制）。

### 验收标准

- 一个全新的云端 Agent 沙箱，只被告知"运行 `curl -fsSL https://th.reorx.com/install.sh | sh`，然后读 `tinyhost skill`"，就能完成安装、申请授权、预览、发布，并把版本链接和主入口告诉我。
- 我在手机上收到授权通知，点开、批准，这个 Agent 随即可用。
- 一个 Agent 发布 App 包、另一个 Agent 推数据，两者互不覆盖；任何一次发布都能一键回滚。
- 私有 App 在没登录的浏览器里打不开；登录后能看，但这个浏览器里的任何 App 页面都不能执行受控操作。
- 服务器丢失后，能从备份恢复全部 App、版本和 Agent。

## Tech Design

### 现状

空仓库。参考同一作者的 Go 服务 `~/Code/hookploy`：无 CGO、`modernc.org/sqlite`（DSN 带 `_pragma=busy_timeout(5000)&_pragma=journal_mode(WAL)&_pragma=foreign_keys(1)`，`SetMaxOpenConns(1)`，迁移用 `PRAGMA user_version`）、CLI 用 stdlib `flag` 加 `register(&command{...})` 分发、`internal/api` 放共享 DTO、`internal/token` 生成带前缀的 token 并只存 SHA-256、`--json` 输出用 golden 快照测试（`go test ./internal/cli -update`）、`make dist` + `v*` tag 触发 GitHub Release、版本号用 `-ldflags -X` 注入 `internal/version.Version`。tinyhost 沿用这些约定。

### 方案

一个 Go module（`github.com/reorx/tinyhost`），产出两个二进制：

- `tinyhost`：Agent 用的 CLI，交叉编译到 linux / darwin / windows × amd64 / arm64。
- `tinyhost-server`：服务端。一个进程按请求的 Host 分流：apps 域名提供内容和 Agent API，admin 域名提供后台。

存储用 SQLite 放元数据，文件内容按 sha256 存在本地目录里（内容寻址、自动去重）。前面由 Caddy 终止 TLS。

关键决策：

1. **apps 域名路径式托管，后台单独一个域名。** 这是用户的决定。被否决的方案：每个 App 一个子域名（要通配符证书和第二个注册域名，部署重）。代价见"风险与待定"。
2. **安全边界按凭证类型划分，而不是按请求来源。** 同一个 apps 域名下，服务器分辨不出请求来自哪个页面（cookie、Origin 都一样，Referer 能被脚本改），所以：
   - Agent API 只认 `Authorization: Bearer`，不读任何 cookie，不发 CORS 头。
   - apps 域名上唯一的 cookie 是私有 App 的查看会话 `__Host-th_view`，服务端没有任何接口能用它做"读内容"以外的事。
   - 后台在 admin 域名，会话 cookie `__Host-th_admin` 是 host-only 的：apps 域名的脚本读不到，也没法种。但两个域名同属 `reorx.com`，是"同站"，SameSite 挡不住从 App 页面发起的表单 POST。所以后台所有写操作都要校验 `Origin` 等于 admin 源（没有 `Origin` 时退而检查 `Sec-Fetch-Site: same-origin`），不满足就 403。
   - 密码只在 admin 域名输入。私有 App 的查看会话由 admin 域名签发一次性票据，跳回 apps 域名兑换；apps 域名上不出现密码框。
   - 用户内容永远不挂在根路径 `/` 和 `/_/` 下；服务端从不发送 `Service-Worker-Allowed`，App 的 Service Worker 作用域只能在自己的路径前缀内。
3. **两个二进制，不做成一个带子命令的二进制。** Agent 下载的 CLI 小，help 里只有 Agent 用得到的命令。被否决：hookploy 式的单二进制，那样服务端代码和后台模板都会打进 CLI。
4. **版本由层组合而成。** 一次上传生成一个"层"（一组 路径→文件块）。版本记录一个 App 包层和若干覆盖目录层。发布 App 包时换掉包层、保留覆盖层；推数据时换掉对应目录的覆盖层。文件块去重，新版本几乎不占空间。被否决：每个版本存一份完整的文件清单（推一次数据就要复制整个 App 的清单，也表达不了覆盖目录的归属）。
5. **新版本总是在"主入口当前指向的版本"上替换一层。** 回滚之后再推数据，不会把坏掉的新版代码带回来。被否决：基于编号最大的版本。
6. **上传格式是单个 tar.gz 请求。** curl 一行就能发（没装 CLI 的 Agent 也能用），服务端边解包边入库去重。被否决：here.now 式的"先报清单、再传缺失文件、最后 finalize"——省带宽，但多两轮请求和一个中间状态，在 50MB 上限下不值得。
7. **CLI 用 stdlib `flag`；后台用 `html/template` + `embed` 做服务端渲染的表单页。** 不引入 cobra，也不要前端构建。hookploy 的 webui 用 templ；tinyhost 的后台只有几个表单页，用标准库省掉代码生成，开源贡献者也更容易上手。

### 仓库结构

```
cmd/tinyhost/            CLI 入口
cmd/tinyhost-server/     服务端入口（serve / passwd / token / gc）
internal/api/            HTTP API 与 CLI 共用的 DTO，也是 --json 的输出结构
internal/version/        版本号，-ldflags 注入
internal/token/          token 与会话 ID 的生成、哈希、比较
internal/slug/           slug 校验、保留字、@vN 解析
internal/bundle/         CLI 侧打包（排除规则、tar.gz、路径检查）与服务端解包校验、tinyhost.json
internal/blob/           内容寻址文件块存储
internal/store/          SQLite schema、迁移、查询
internal/server/         HTTP：按 Host 分流、内容托管、Agent API、后台、中间件、GC
internal/server/views/   后台模板与静态资源（embed）
internal/notify/         ntfy / webhook（M3）
internal/cli/            CLI 命令、配置、输出
skill/                   SKILL.md（embed，CLI 与服务端共用）
```

服务端核心代码不 import `notify`，只持有事件回调，由 `cmd/tinyhost-server` 接线（同 hookploy）。

### 测试方式（各期通用）

按 BDD：每期先把 spec 的验收标准写成行为测试，再实现。

- 服务端：`httptest.Server` 起完整服务，请求时设置 `Host` 头来模拟两个域名。测试名写成行为句子（如 `TestDeployCreatesVersionAndReturnsTwoURLs`），函数上方加一行 `// Behavior:` 注释（同 hookploy）。
- CLI：进程内执行命令、指向测试服务器、断言输出；`--json` 输出用 golden 快照。
- 本地手动验证：apps 域名用 `http://localhost:3471`，admin 域名用 `http://admin.localhost:3471`（浏览器会把 `*.localhost` 解析到本机），服务端加 `--insecure-cookies`。截图归档到 `tmp/<日期>-<任务>/`。

### 风险与待定

- **同站风险（已接受）**：任何 App 都能画一个假登录框；在登录过私有 App 的浏览器里，一个 App 的脚本能读到其他私有 App 的内容，并发到外网。只托管自己 Agent 产出的内容时可以接受。要写进 README 的安全说明。
- **`reorx.com` 下的其他服务**：`th.reorx.com` 上的不可信脚本和 linkmind、memos 等服务属于同站，可以带着它们 SameSite=Lax 的 cookie 发表单 POST，也可以给 `.reorx.com` 种 cookie。这些服务各自的 CSRF 防护没有核实过。M4 上线前，列出 reorx.com 下所有用 cookie 会话的服务，逐个确认。
- **Cloudflare 拦截云端 Agent**：Agent 的出口是机房 IP。如果 reorx.com zone 开了 Bot Fight Mode（免费套餐不能用 WAF 规则按路径豁免），API 请求会被质询。M4 先核实。
- **名字**：开源后和商业服务 tiiny.host 名字相近。用户决定暂不改名。
